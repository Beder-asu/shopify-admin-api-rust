The TS ➔ Rust Translation Guide

This is a low-level, module-by-module breakdown of how the Shopify Typescript SDK was manually ported into idiomatic Rust. It explains the purpose of every file, how data flows through the application, and why specific Rust paradigms were chosen to replace TS patterns.

1. shopify-core/src/session.rs

This module replaces the TS Session class. In TS, a Session is a stateful object. In Rust, we split it into a pure data struct (Session) and its implementation block (impl Session).

TypeScript (Class)

export class Session {
  public id: string;
  public shop: string;
  public state: string;
  public isOnline: boolean;
  public scope?: string;
  
  constructor(params) { ... }
  public isActive(scopes): boolean { ... }
  public toPropertyArray(): Property[] { ... }
}

Rust (Struct + Impl)

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Session {
    pub id: String,
    pub shop: String,
    pub state: String,
    pub is_online: bool,
    pub scope: Option<String>,
}

impl Session {
    pub fn new_offline(...) -> Self { ... }
    pub fn is_active(&self, req_scopes: &AuthScopes) -> bool { ... }
    pub fn to_property_array(&self) -> Vec<(String, String)> { ... }
}
Low-level implementation detail: Notice how TS scope?: string becomes Rust Option<String>. In to_property_array, we match the exact TS tuple format by returning a Vec<(String, String)>. This makes it a 1-to-1 drop-in for Redis/Postgres storage adapters that expect key-value pairs.

1. shopify-core/src/auth/scopes.rs

This module replaces the TS AuthScopes string manipulator. Shopify scopes are comma-separated strings (e.g. "read_products,write_orders"). The complexity comes from the fact that write_x implicitly grants read_x.

The BTreeSet choice

In TS, scopes were split into arrays. In Rust, we parse the comma-separated string into a BTreeSet<String>. We chose BTreeSet over HashSet so that the scopes are naturally sorted alphabetically, allowing deterministic comparisons when converting back to a string.

pub fn has(&self, required: &AuthScopes) -> bool {
    required.scopes.iter().all(|scope| {
        self.scopes.contains(scope) || self.implied_by(scope)
    })
}

fn implied_by(&self, scope: &str) -> bool {
    if let Some(resource) = scope.strip_prefix("read_") {
        self.scopes.contains(&format!("write_{}", resource))
    } else { false }
}

1. shopify-core/src/crypto.rs

This replaces the TS `crypto` utilities used to verify Shopify Webhooks and OAuth callbacks.

We use the hmac and sha2 crates. The most critical function is validate_hmac, which calculates a SHA256 HMAC of the raw request body using your app's `API_SECRET_KEY` and compares it to the X-Shopify-Hmac-Sha256 header.

Security detail: We strictly use subtle::ConstantTimeEq to prevent timing attacks. In TS, you would use crypto.timingSafeEqual. In Rust, the hmac crate handles this automatically when you call mac.verify_slice(...).

1. shopify-core/src/error.rs

Instead of throwing custom Error classes like ShopifyError extends Error, we define a comprehensive enum using the thiserror macro.

The ShopifyError::from_response(status, body) function is the central parser that maps raw HTTP 4xx/5xx status codes directly to Rust types like Unauthorized(String), RateLimited { retry_after: u64 }, and GraphQLError(Vec<GraphQLErrorDetail>).

2. graphql-port/src/client.rs

This is the heart of the modern GraphQL architecture.

The Dual-Throttle Engine

Shopify GraphQL rate limiting is extremely complex because it throttles you at two different layers:

  1. HTTP Layer (429): The HTTP request itself is rejected before reaching GraphQL.
  2. GraphQL Layer (200 OK + "Throttled" error): The HTTP request succeeds, but the GraphQL engine rejects it due to query cost.

Our send_graphql_payload function is an infinite loop {} that handles both. If it receives a 429, it reads the Retry-After HTTP header and calls tokio::time::sleep. If it receives a 200 OK but the JSON contains errors: [{ message: "Throttled" }], it parses the GraphQL Extensions node to extract the restore_rate and calculates the exact mathematically optimal sleep time: (1.0 / rate) + 0.5 seconds.

if is_throttled && retries < MAX_RETRIES {
    retries += 1;
    let sleep_time = gql_response.extensions
        .as_ref().and_then(|ext| ext.cost.as_ref())
        .map(|cost| {
            let rate = cost.throttle_status.restore_rate.max(1.0);
            Duration::from_secs_f64((1.0 / rate) + 0.5) // Auto-calculate sleep!
        }).unwrap_or(Duration::from_secs(2));
    sleep(sleep_time).await;
    continue;
}

2. graphql-port/src/graphql.rs & models.rs

Because GraphQL uses Relay-style pagination, these files define the reusable wrappers:

pub struct Connection<T> { pub edges: Vec<Edge<T>>, pub page_info: PageInfo }
pub struct Edge<T> { pub cursor: String, pub node: T }

These generic bounds allow developers to easily deserialize deeply nested Shopify pagination trees without writing massive boilerplate structs.

2. graphql-port/src/generated.rs

This replaces Apollo Client codegen. We use the graphql_client crate. By pointing it to schema.graphql and queries.graphql, it executes a procedural macro at compile time to generate exact Rust structs for the Request and Response.

When you call client.send_query(shop_details::Variables), the compiler enforces that you are passing the exact variables required by your .graphql file, and returns a fully typed shop_details::ResponseData.

3. rust-port/src/client.rs

The legacy REST client. It uses reqwest to perform GET, POST, PUT, DELETE.

It utilizes the serde::de::DeserializeOwned trait bound everywhere. This means the JSON returned from response.text() is fed directly into serde_json::from_str::<T>(&body).

Like the GraphQL client, it features a send_with_retry function that loops on HTTP 429 statuses, extracting the Retry-After header.

3. rust-port/src/config.rs & shopify.rs

These modules represent the app initialization phase. In TS, you call shopifyApi({ apiKey: '...', scopes: [...] }). In Rust, you initialize a ConfigParams struct, which is validated and converted into an immutable, thread-safe Config struct.

The ShopifyApp struct acts as the central factory. It holds an Arc<Config> (Atomic Reference Counted pointer). When you call app.rest_client(&session), it creates a lightweight clone of the configuration pointer and pairs it with the Session's access token to instantiate a Client.
